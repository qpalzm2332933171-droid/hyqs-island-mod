## 1. 失败原因: checkMailLegal(token 校验)

从设备动态解密出的游戏主逻辑 `project.js` (Frida hook `xxtea_decrypt` 得到) 中, 
`DYHttpMgr` 模块 `queryMail` 的实现 (美颜后行号 4994-5013):

```js
queryMail: function(e, t) {
  ...
  this._requestCommon(function(e, a) {
    ...
    for (var n = a.data.goods_from_channel, o = n.length - 1; o >= 0; o--)
      if (!i.checkMailLegal(n[o])) { ...; n.splice(o, 1); }   // 校验失败 -> 从列表剔除
    for (var c = (n = a.data.goods_from_user).length - 1; c >= 0; c--)
      if (!i.checkMailLegal(n[c])) { ...; n.splice(c, 1); }
    t && t(e, a);
  }, n, a, "POST");
},
checkMailLegal: function(e) {
  for (var t = "", a = ["id","type","goods","to_user","createTime","deadline","coin"], n = 0; n < a.length; ++n) 
    t += e[a[n]];
  return dy.crypto.md5.hex_md5(t + d) == e.token;
},
```

密钥 `d` 定义在同模块头部 (行 3946):

```js
d = "apsdfAJOJ(#@&($0809283JLJOOJ",
```

### 完整公式

```
token = MD5( id + type + goods + to_user + createTime + deadline + coin + "apsdfAJOJ(#@&($0809283JLJOOJ" )
```

- 拼接顺序固定: `id`, `type`, `goods`, `to_user`, `createTime`, `deadline`, `coin`, 再拼密钥;
- 全部按 JS 字符串拼接 (数字转十进制字符串), UTF-8 编码后 MD5 取 32 位小写 hex;
- **不参与 token** 的字段: title, message, nick, from_user, channel, is_receive, is_open, valid, id/coin 之外的其他任何字段。

### 为什么你之前的测试会失败

- 你把 `100002:2` 改成 `100002:6`、`2800` 改成 `2801`、`4438:8` 改成 `4438:10` 时, 
  goods/coin 变了但 token 没变 → `checkMailLegal` 返回 false → 客户端把该邮件从列表里 `splice` 删除 
  → 表现为"邮件不显示/无法解析"。
- 与 createTime/deadline/token 的时间戳完全无关: 你的替换里 deadline 是 2022 年也照样能显示。

## 2. 显示链路 (为什么替换响应体能生效)

1. `PanelMail.start` → `dy.http.queryMail` → POST `/Logic/user/querymail1` (行 42315-42327);
2. 响应经 `JSON.parse`, 逐封 `checkMailLegal` 过滤 (token 不对的邮件被删除);
3. `PanelMail.layoutUI`: 邮件显示条件 = `base.mailList[id] != 2 && !is_receive` (行 42328-42341);
4. 打开详情 `PanelMailDetail` (行 41789+): 标题/正文/物品图标均来自响应体;
   - 物品图标仅对 `item_profile` 中存在的 id 显示 (行 41833-41840);
5. `dy.realTime.currentTick()` 只用于截止时间倒计时显示 (行 41962-41971), **不影响能否显示/领取**;
6. 客户端有 10 分钟邮件缓存 (`MAIL_CACHE_TICK: 6e5` 行 2498), 改规则后需重启游戏或等缓存过期。

## 3. 领取链路 (邮件不在服务器上也能拿到东西?)

`PanelMailDetail.getItem()` (行 41870-41935):

1. 先 POST `/Logic/user/updatemail` (`{id}`), **要求响应 `errorCode == 0`**;
2. 成功后客户端本地发放奖励 (服务器不校验内容):
   - 普通物品 → `HYBag.updateAttr(c)` **直接写背包, 无负重上限** (行 12206-12225);
   - 100000 → 书页(scriptChange 上报); 100002 → 求生精选; 100003 → 天赋原石; 
     100004 → 天赋结晶; 100005 → 时之沙(广告币); 100006 → 神秘钥匙;
   - `coin` → `HYCoin.update` 直接加贝壳 (行 12455);
   - 甚至 `base.xxx` / `core.xxx` 开头的条目能直接写存档字段 (行 41910-41912)。
3. 之后 `HYData.trySave()` + 服务器日志上报(logItem/saveCoins 等, 仅日志性质)。

### 关键结论: 领取能否成功取决于 `updatemail` 的服务器响应

- 客户端发放奖励前**唯一**的服务器门槛是 `updateMail` 返回 `errorCode == 0`;
- 邮件 id 若服务器认识 (真实存在的未领取邮件 id) → 基本必过;
- 邮件 id 若是伪造 id → 需要实测服务器是否对未知 id 也返回 0 (待验证);
- `channel == "_"` 的邮件领取后**不写入**本地 `base.mailList[id]=2` 标记 (行 41922), 
  意味着同一 id 每次重开游戏都可能再次领取 (可重复领取的潜力点, 待实测)。

## 4. 游戏存档的信任模型 (为什么这条路成立)

- 背包/货币等核心数据在**客户端本地**, 由 `updateData` 接口定期同步回服务器,
  其 `sign = md5(密钥d + base64(modify) + uid)` (行 4614) —— 服务器信任客户端提交的数据;
- 邮件奖励的发放完全在客户端完成, 服务器只负责"标记已领取"和"记录日志";
- 因此代理替换响应体 + 重算 token = 客户端显示什么, 就能领什么。
